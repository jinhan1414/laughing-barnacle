## Context
现有聊天是同步推理主链路，模型在一次请求里完成“判断、工具调用、最终回复”。  
如果直接把 `/chat/send` 统一改为异步，会把“何时转后台”的决策从 LLM 拿走，不符合当前“执行链路优化优先依赖模型能力”的约束。

当前已有可复用基础：
- 会话可由后台流程追加 assistant/event（定时任务已验证）
- 聊天页已轮询 `/api/chat/updates` 获取主动增量

因此本次方案采用“LLM 决策 + 平台提供后台执行能力”，而不是“后端硬编码全量异步”。

## Goals / Non-Goals
- Goals:
  - 由 LLM 自主判断任务是否需要转后台执行
  - 提供标准后台任务能力，支持提交、查询、取消与可观测状态
  - 后台完成后唤起数字分身向用户主动通知结果
- Non-Goals:
  - 不将所有聊天请求强制改为异步
  - 不引入关键词/正则分流规则
  - 首版不做跨进程恢复与分布式任务队列

## Decisions
### Decision 1: 新增内置 Skill（策略层）+ 内置工具（执行层）
新增内置 Skill：`async-task-orchestrator`，用于提示模型何时转后台、如何选择工具调用顺序。  
该 Skill 仅做策略提示，不直接执行 HTTP 调用。

新增内置工具集合（名称固定）：
- `async_task__submit`：提交后台任务，返回 `task_id/status`
- `async_task__get`：查询任务状态、结果与日志
- `async_task__cancel`：取消可取消任务

参数契约固定如下：
- `async_task__submit`
  - 必填：`task_type`（`generic|a2a`）、`request`（任务目标）
  - 条件必填：当 `task_type=a2a` 时，`agent_id`、`agent_input`
  - 可选：`dedupe_key`、`notify_on_finish`（默认 `true`）、`metadata`
- `async_task__get`
  - 必填：`task_id`
  - 可选：`include_logs`（默认 `false`）、`log_cursor`、`log_limit`（默认 20，上限 200）
- `async_task__cancel`
  - 必填：`task_id`
  - 可选：`reason`

LLM 在正常回复流程中可主动调用这些工具；工具结果先返回给模型，再由模型组织面向用户的自然语言输出。  
是否调用由模型基于上下文自主判断，后端不额外加“自动分流规则”。

### Decision 2: `/chat/send` 保持同步入口，异步作为模型可选分支
`/chat/send` 仍走现有 `HandleUserMessage` 入口；  
区别在于模型现在可在工具回合中把任务转为后台，`submit` 结果先回给模型（含 `task_id/status`），再由模型决定本轮如何对用户表达。

这样保留短任务直答体验，同时让长任务具备后台化能力。

### Decision 3: 后台任务执行与聊天主链路解耦
后台运行时（建议新模块）负责：
- 任务持久化最小元信息（`task_id/status/input/created_at/updated_at/error`）
- goroutine 执行与状态流转（`submitted -> working -> succeeded|failed|canceled`）
- 结果产物落盘并可被 `get` 查询

任务执行可复用 Agent 能力，但与“当前 pending user 回合”隔离，避免破坏现有重试契约。

对于 A2A 类型任务，后台运行时承接“回合外跟踪”职责：
- 提交阶段由后台运行时创建远端 A2A 任务并记录远端 `task_id`
- 跟踪阶段在后台按策略查询终态
- 终态后统一走通知流程回写会话

### Decision 4: 完成后“唤起数字分身”生成通知消息
后台任务终态后，系统需触发一次数字分身通知流程：
- 成功：生成用户可读完成通知（含关键结果摘要）
- 失败：生成用户可读失败通知（含错误摘要）

通知以 assistant 消息写入会话，并可附带结构化事件证据，确保前端通过 `/api/chat/updates` 自动看到。

### Decision 5: 防止通知链路递归膨胀
通知生成链路使用独立 purpose/约束，禁止再次提交新的后台任务，避免“后台完成 -> 再转后台”的递归循环。

### Decision 6: 固定注入后台任务索引（渐进式披露）
在每轮请求上下文中固定注入后台任务索引，形态对齐现有 Skill/A2A 索引策略：
- 仅注入“当天任务 + 仍在运行任务”的轻量字段：`task_id/status/created_at/updated_at/brief`
- 默认不注入全量日志正文，避免上下文膨胀
- 模型需要细节时再调用 `async_task__get` 或只读接口按需读取

该决策保证模型具备“已存在后台任务”的稳定感知，避免重复提交同类任务。

### Decision 7: 设置页提供后台任务清单与全量日志
设置页新增后台任务可观测区域，支持：
- 查看全部后台任务清单（运行中 + 历史）
- 查看单任务全量日志（状态流转、关键步骤、错误信息、通知结果）

该能力用于普通用户与研发排障统一入口，不依赖日志页手工筛选。

### Decision 8: A2A 执行入口收敛为 Async Task（不保留旧工具兼容）
本次改造将模型侧 A2A 直接工具入口收敛为单一路径：
- 移除模型可见的 `a2a__send/get/cancel`
- 模型发起 A2A 任务时统一调用 `async_task__submit(type=a2a)`
- 查询与取消统一通过 `async_task__get/cancel`

该决策用于减少模型分支选择成本，避免同类能力在工具层重复暴露。

## Risks / Trade-offs
- 风险：模型不调用 `submit` 时仍是同步体验。  
  缓解：通过 runtime prompt 清晰声明“长任务可转后台”能力，提高触发稳定性。
- 风险：后台任务与主对话并行，可能出现结果插入时序差异。  
  缓解：所有通知带 `task_id` 与时间戳，前端按 created_at 展示。
- 风险：通知文案质量不稳定。  
  缓解：通知链路固定结构化输入，并保留错误直出兜底文案（显式、可观察）。
- 风险：A2A 远端任务长期不终态导致后台任务悬挂。  
  缓解：为 A2A 类型后台任务设置最大跟踪窗口与显式超时终态（`failed` + 原因）。
- 风险：移除 `a2a__*` 属于破坏性变更。  
  缓解：在提案与发布说明中明确迁移规则：A2A 调用统一改用 `async_task__submit(type=a2a)`。
- 风险：固定注入后台任务索引可能增加 token 开销。  
  缓解：索引仅保留“当天 + 运行中”任务和必要字段，详情按需读取。
- 风险：全量日志展示可能暴露内部噪声信息。  
  缓解：设置页默认按任务折叠展示，并提供结构化字段优先视图。

## Migration Plan
1. 定义后台任务数据模型、状态机与最小运行时接口。
2. 增加内置 Skill `async-task-orchestrator`（策略提示）并接入技能索引。
3. 增加内置 `async_task__submit/get/cancel` 工具定义与分发。
4. 把后台任务能力注入模型上下文与运行时约束文案。
5. 增加后台任务索引固定注入（当天+运行中）与按需详情读取路径。
6. 增加任务完成后的数字分身通知流程，并写入会话。
7. 扩展 `/api/chat/updates` 与前端渲染，确保状态与通知可见。
8. 设置页新增后台任务清单与全量日志视图。
9. 增加回归测试覆盖 skill 命中、submit/get/cancel、索引注入、完成通知、失败通知与禁递归。
10. 增加 A2A 一体化回归：移除 `a2a__*` 暴露、A2A 提交后台承接、回合外查询、终态通知与证据落盘。
